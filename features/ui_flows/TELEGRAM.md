# Telegram-пилот, меню и опрос: этапы 3–8

После применения миграций и запуска обновлённого бота администратор может отправить
`/flow_demo` в приватном чате, чей ID совпадает с Settings.admin_chat_id.
Команда регистрируется только в административном списке команд. В других чатах
она не запускает сценарий. Если admin_chat_id указывает группу, пилот в ней недоступен:
для пилота нужен административный приватный чат.

Команда создаёт и публикует встроенный `ui_flow_demo` только при первом запуске.
Она не заменяет существующую схему. Повторный вызов восстанавливает активный шаг,
не исполняя предыдущие Action. После завершения формы команда начинает новую сессию.
Основное меню и «Учёба» перенесены для приватного администратора на этапе 6.
На этапе 7 `/start student_questions` запускает граф для администратора; уже начатый
legacy-опрос и остальные пользователи сохраняют прежний маршрут. [Подробности](SURVEY.md).
Административный `/start` открывает опубликованный `main_menu`; Back отменяет форму
и возвращает текущую версию корня. Переходы в девять прежних функций выполняются
через общие presentation entry points. Подробности: [MONITORING.md](MONITORING.md).

## Контрольный проход

1. Отправить `/flow_demo` и выбрать «Открыть форму».
2. Ввести от 1 до 120 символов. Неверный ввод сохраняет текущий шаг.
3. На inline-клавиатуре выбрать, показывать ли текст в результате, либо вернуться
   к редактированию или отменить форму.
4. Для восстановления шага после перезапуска снова отправить `/flow_demo`.
5. Для выхода также можно воспользоваться обычной глобальной навигацией бота.

Встроенный пример проходит через Action, Menu, Input, Condition и End. Его Action
только читает наличие ответа через StudentQuestionsService; пример не отправляет
и не заменяет реальные ответы опроса. Введённый текст хранится в состоянии тестовой
формы и, если показан, в снимке подготовленного экрана. В аудит ввод попадает как
`[masked]`. Перед production-включением обычных форм нужна политика очистки этих данных.

## Границы транзакций

Порядок внешних middleware: RateLimit, PerChatOrdering, AfterRequest, Dishka, Locale.
Внутренние: PrivateChatOnly, UiFlowNavigation, UiFlowObservation, ActionLog. Существующие взаимные порядки
проверки приватности, аудита, локали и DI сохраняются; добавлены два явных участка.

Runtime-handler ставит действие в AfterRequestActions, затем возвращается. Сначала
нормально завершается исходный REQUEST: сохраняются профиль и аудит. Только после
его commit APP-координатор открывает свой REQUEST. Это важно для первого обращения:
иначе незавершённый upsert пользователя удерживает блокировку, требуемую дочерней
транзакции для FK сессии или записи делегата.

В scope координатора переход, бизнес-запись делегата, дедупликация и подготовленный
экран сохраняются атомарно. Renderer выполняется до commit; ошибка разметки или
подстановки откатывает переход. Затем отдельный короткий REQUEST переводит intent
из pending в unknown. Telegram вызывается после завершения обоих scopes.
При успехе ещё один REQUEST записывает sent и message_id.

Ошибка commit не приводит к отправке. Ошибка сети, неопределённый результат,
cancellation после начала отправки или частичный результат оставляют unknown.
Такой intent автоматически не повторяется. Явное восстановление создаёт новый
экран текущего шага без повторного бизнес-действия. Постоянная ошибка получателя
устанавливает общий bot_stopped и помечает intent failed.

Очередь одного чата остаётся заблокированной до конца доставки. Это порядок одного
процесса long polling; упорядоченная доставка из нескольких разных процессов не
заявляется. Защита состояния в БД остаётся отдельной и проверяется конкурентными тестами.

## Экраны и кнопки

`ui_screen_deliveries` хранит снимок текста, клавиатуры, локали/темы, ссылку на сессию,
ревизию, update_id, статус и Telegram message_id. Событие имеет не более одного intent.
Callback содержит случайный 96-битный токен длиной 16 символов и индекс кнопки.
Typed CallbackData остаётся короче 64 байт независимо от длины ID узла/кнопки в схеме.

Обработчик проверяет чат, пользователя, сообщение, ревизию, тип и доступность кнопки.
URL-кнопка не продвигает состояние. Старый callback получает локализованное сообщение.
Ответ callback выполняется после фиксации перехода, до отправки нового экрана;
при отказе или неожиданной ошибке также предпринимается попытка ответить на callback.

Reply-текст сопоставляется с последним показанным снимком текущей ревизии, а не
с заново вычисленным переводом. Неоднозначные подписи отклоняются. Смена локали
или темы сохраняет форму и после commit перерисовывает текущий шаг в новом контексте.
Другой совпавший legacy-handler отменяет runtime-сессию после своего REQUEST;
глобальная Studies/Back навигация по-прежнему предшествует обработчику ввода.
Совпавшая с текущим показанным reply-снимком кнопка имеет приоритет над глобальным
текстовым переходом: схема сохраняет настроенную цель кнопки.

Для inline-экрана сначала отправляется текст с ReplyKeyboardRemove. Затем отдельный
sendMessage отправляет локализованное «Выберите действие» с готовой inline-клавиатурой.
Intent хранит message_id второго сообщения, поскольку именно оно содержит callbacks.
Telegram запрещает редактировать сообщение с ReplyKeyboardRemove: прежняя попытка
attach через editMessageReplyMarkup воспроизводилась как `message can't be edited`.
См. [ограничение редактирования](https://core.telegram.org/bots/api#updating-messages).
Если второй send не удался, состояние уже сохранено, доставка остаётся unknown;
повтор события не отправляет его заново, явное восстановление возвращает экран.

Текущий renderer поддерживает текст до 4096 UTF-16 единиц после разбора HTML,
подписи до 64 UTF-16 единиц и ограниченный набор HTML-тегов. Динамические значения
экранируются для тела сообщения; подписи кнопок остаются обычным текстом.
Произвольный HTML и JavaScript не исполняются. Эти проверки не обещают поддержку
всех расширений Telegram HTML; редактор должен предлагать поддерживаемое подмножество.

## Проверка

- PostgreSQL и настоящий Dispatcher: первый профиль, commit до сети, переходы,
  старые кнопки, маскирование аудита, локаль, отмена и восстановление в новом контейнере.
- Отдельные тесты: ошибка commit не отправляет экран; очередь чата включает сеть;
  timeout не запускает автоматический повтор.
- Renderer: пять локалей, обе темы, HTML-экранирование, fallback, лимиты и токены.
- Миграция f4e620d67ed7: upgrade/downgrade в изолированной схеме с сохранением старых данных.
- Общий прогон: 850 passed, 28 skipped; Ruff, format, strict mypy, schema export и alembic check прошли.
- Дополнительно: 5 HTTP-тестов настоящего aiohttp-клиента aiogram через локальную
  Postman-симуляцию, включая существующую доставку рассылки. Симуляция не обращается
  к Telegram и использует только вымышленные токены/получателей.

Повтор HTTP-проверки:

```powershell
postman simulation run postman/simulations/telegram.sim.yaml --port 4513 --output ndjson --no-history
# В другом терминале, с development DB и остальными тестовыми env из AGENTS.md:
$env:MANASHELPER_TELEGRAM_SIMULATION_URL='http://localhost:4513/telegram'
.venv/Scripts/python.exe -m pytest tests/modules/ui_flows/test_telegram_http.py tests/modules/broadcast/test_telegram_http_delivery.py -q
```

Исправленный sender проверен на живом тестовом боте в приватном чате администратора:
два sendMessage приняты, ID второго сообщения возвращён для проверки callbacks.
Обе диагностические отправки удалены. Симуляция теперь отклоняет редактирование
ReplyKeyboardRemove; актуальный HTTP-прогон — 9 passed. Полный ручной проход формы
в Telegram-клиенте остаётся отдельной проверкой перед production-включением.
Рабочий бот во время разработки не запускался и не перезапускался.
