# Runtime сценариев: композиция v2 и внешние операции

Реализованы исполнитель между пользовательскими событиями, PostgreSQL-хранилище,
Dishka-композиция, Telegram-адаптер, административный API и Vue-редактор.
Этапы исходного [UI_FLOW_EDITOR_PLAN.md](../UI_FLOW_EDITOR_PLAN.md) описывают редактор.
В отдельном [ORCHESTRATION.md](ORCHESTRATION.md) этапы 5–6 добавляют композицию,
структурированные данные, динамические экраны и внешние эффекты. Эти механизмы
реализованы; массовый перенос feature UI и удаление FSM остаются этапами 7–12.
Меню/опрос выбирают runtime через опубликованные bindings и режим admin/all/off;
активные legacy-формы сохраняют владельца. Жизненный цикл доставки описан в [TELEGRAM.md](TELEGRAM.md),
общая проекция положения пользователей — в [MONITORING.md](MONITORING.md).

## Приложение

Чистый движок находится в `src/ui_flows/`, его хранилище задаётся контрактами
`ports/repositories.py`. Интеграции и DI находятся в `src/manashelper/modules/ui_flows/`.
Общая SQLAlchemy Base находится в `src/common/database.py`.

- `application/flows.py::FlowService`: создание и чтение черновика, сохранение с
  expected_revision, публикация и активация существующей версии.
- `application/dialogs.py::DialogService`: запуск, чтение состояния и обработка
  нормализованного события с проверкой пользователя, ревизии и update_id.
- `application/interpreter.py::FlowInterpreter`: локальное исполнение узлов до
  ожидания или завершения. SQL и Telegram внутри исполнителя отсутствуют.
- `application/execution.py::ScenarioExecutor`: Call/Return/Replace, восстановление
  durable frames, изоляция локальных данных и общий бюджет автоматических шагов.
- `application/delegates.py::DelegateRegistry`: явные async-делегаты с версией
  контракта и проверкой типов аргументов, выходов и исходов.
- `manashelper/modules/student_questions/survey_delegates.py`: адаптеры к StudentQuestionsService.
- `manashelper/modules/users/ui_delegates.py`: транзакционные смены locale/theme.
- `manashelper/modules/ui_flows/application/effect_worker.py::EffectWorker`: APP worker,
  который выполняет явно зарегистрированные external delegates после commit claim.
- `manashelper/modules/ui_flows/provider.py::UiFlowsProvider`: REQUEST-зависимости
  приложения и APP worker/coordinator. Полная композиция находится в `main.py`;
  standalone-контейнеры также предоставляют owning providers пользователей,
  опроса, DB-каталога и Telegram-платформы. До создания вызвать load_models.
  Сам движок импортируется без приложения и ORM.

Provider регистрируется в `main.py`; административный `/flow_demo` остаётся входом
для проверки отдельных сценариев. Реестр содержит два транзакционных делегата опроса
и users.set_locale/users.set_theme; production external registry пока пуст.
Сценарии выбора locale/theme создаются только при отсутствии, без перезаписи
редакторских документов. Их глобальные triggers ещё legacy; Settings и все формы
не считаются перенесёнными. Девять совместимых handoff-возможностей используют
публичные presentation entry points; HTTP preview показывает намерение без вызова
реального адаптера.

## Хранилище

Исходная миграция `84ba87e64380` добавила четыре базовые таблицы:

| Таблица | Содержимое |
| --- | --- |
| ui_flows | Текущий черновик, его ревизия и указатель опубликованной версии |
| ui_flow_versions | Снимок схемы, номер версии, исходная ревизия, автор и время |
| ui_dialog_sessions | Пользователь/чат, закреплённая версия, шаг, статус, данные и ревизия |
| ui_flow_events | Уникальный update_id, сессия, предыдущий/следующий шаг и исход |

Последующие миграции добавляют delivery intents, rollout, monitoring и trigger
releases/receipts. Миграция `2cf16577afaf` расширяет версии immutable dependency pins,
а сессии — frames. `fd0178000ef5` добавляет `ui_external_operations`, `ui_input_secrets`,
waiting_effect и связь screens/location/history с external operation. Новые nullable
поля сохраняют совместимость старых writers/v1. Полный ORM регистрируется явно в bootstrap.

В истории нет текста сообщений и копии полей формы. Данные ответа находятся только
в необходимом состоянии сессии и в таблице владельца бизнес-функции. repr состояния
и InputEvent скрывает ввод; обработчики не должны логировать полные модели и
Pydantic validation input. Закрытые payload и старые экраны очищаются ежедневным
заданием через семь дней; в закрытых старых сессиях также очищаются frames,
external arguments/results и secrets. Активные данные, бизнес-ответы, metadata и
receipts сохраняются. Истёкшие secret handles удаляются worker отдельно от этого
семидневного срока. См. [RELEASE.md](RELEASE.md).

Одна БД предполагает одного Telegram-бота; update_id уникален в пределах этого
экземпляра. Поддержка нескольких токенов потребует отдельного пространства идентичности.

## Публикация и версии

Черновик можно сохранить с семантическими ошибками для последующего редактирования.
Публикация проверяет статический контракт, наличие делегатов, доступных features
и опубликованных сценариев возврата. Чистый контракт допускает самовозврат, но
Telegram-адаптер исполняет `return_flow` атомарно с завершением исходной сессии;
целевая публикация должна начинаться с Menu/Input, ограничивая автоматические циклы.
HTTP-публикация и активация проверяют Telegram HTML, размеры отрендеренных сообщений
и неоднозначность подписей reply-кнопок. Authored rich messages проверяются для всех
локалей/тем; ссылки media/message_source — по типам и предельным размерам коллекций.

Сохранение увеличивает draft_revision. Публикация блокирует строку сценария,
назначает следующий номер версии и меняет указатель в одной транзакции. Повтор
публикации той же ревизии возвращает прежнюю версию и не отменяет сделанный после
неё rollback. Повтор со старой ревизией после нового редактирования даёт конфликт.
Активация версии проверяет expected_published_version и совместимость контрактов.

Начатая сессия всегда читает свою FlowVersion, даже после публикации новой схемы.
У репозитория нет операции изменения снимка версии. Версии делегатных контрактов
в Action также должны оставаться совместимыми: изменение контракта требует нового номера.

Публикация v2 закрепляет версии всех прямых Call/Replace dependencies, чьи публикации
сами содержат собственные pins. Проверяются inputs/outputs/outcomes, отсутствие
рекурсивного dependency graph и максимальная глубина 16. Новая версия ребёнка
не меняет существующую публикацию родителя. Повторная активация и Triggers проверяют
сохранённые pins, а не подменяют их текущими дочерними версиями. Для принятия новых
сценариев или текстов требуется новая draft revision и публикация.

## Транзакции и конкуренция

Запуск и обработка события проходят внутри repository savepoint, использующего
тот же AsyncSession, что делегат и бизнес-сервис. Savepoint не делает commit:
окончательное решение остаётся у CoreProvider при завершении REQUEST.

1. Взять `pg_advisory_xact_lock(chat_id)`, затем загрузить сессию с FOR UPDATE.
   Для первого запуска блокировка работает до появления строки сессии.
2. Проверить владельца, уникальный update_id и expected_revision.
3. Выполнить переходы и транзакционные делегаты до ожидания.
4. Сохранить состояние и запись события; освободить savepoint.
5. Завершить REQUEST. Исключение или cancellation откатывает весь request.

Частичный unique index дополнительно запрещает две активные сессии на один чат.
waiting_effect входит в эту уникальность. Один APP `ChatOrdering` используется
message/callback middleware и завершением эффектов: apply+delivery не может
обогнать новую навигацию и закрыть её устаревшим экраном. Это process lock, а не
DB lock; завершение эффекта закрывает предварительный REQUEST до ожидания gate.
DB chat locks не удерживаются во время внешнего I/O. Исходный update REQUEST
завершается до runtime coordinator.
Разные update_id с одной ревизией конкурируют: один проходит, второй получает
StaleEventError. Повтор того же update_id возвращает текущее состояние с исходом
duplicate, не повторяя действие; состояние может быть уже дальше первоначального
ответа. Для invalid_input событие учитывается, но шаг, данные и ревизия не меняются.

Если вызывающий код перехватил ошибку, savepoint всё равно отменяет запись делегата,
переход и дедупликацию этого события. Тот же update можно безопасно повторить после
устранения ошибки. Ожидаемый исход делегата, например already_submitted, проходит
обычным переходом. Внешние HTTP-операции и записи запрещены внутри транзакционного
делегата; они выполняются только через durable external operation.

## Внешние операции и sensitive input

External Action останавливает исполнение в waiting_effect. Состояние и операция
pending сохраняются в одной REQUEST-транзакции. Уникальность session/revision/node
не позволяет повторно подготовить другую операцию для той же позиции.

1. Worker берёт короткий chat lock, проверяет исходные session/flow/version/node/revision
   и активность исполнения, затем атомарно переводит pending в unknown.
2. REQUEST и unknown commit завершаются до расшифровки и вызова external handler.
   Во время I/O нет DB chat lock; delegate получает явные locale/theme и pinned
   text snapshot. Ошибки логируются типом и стабильным error_code, без payload.
3. Проверенный DelegateResult сохраняется как succeeded. Отдельный REQUEST применяет
   его только к той же активной waiting_effect позиции; отменённую или заменённую
   форму результат не открывает. Поздний результат отмечается applied без UI-перехода.
4. При успешном продолжении state, transactional delegates, projection/history,
   operation applied и screen intent фиксируются вместе. Сама доставка идёт после commit.

Конкурирующий claim проходит только один раз. Worker восстанавливает pending работу,
succeeded результаты и applied операции с ещё pending screen intent. Unknown
операции и unknown/sent deliveries автоматически не повторяются; failed операция
также терминальна. Cancellation после claim сохраняет unknown. Это предотвращает
повтор внешней записи, но не обещает exactly-once Telegram и не доказывает, завершился
ли upstream side effect перед потерей ответа. Worker опрашивает bounded batch до
100 операций каждые пять секунд и закрывается до DI/HTTP/DB ресурсов.

Secret input сохраняет в DialogState только непрозрачный UUID handle. Шифротекст
AES-GCM хранится отдельно с AAD secret/session/user/chat и сроком пять минут.
Worker проверяет владельца/expiry, раскрывает plaintext только в памяти после
commit claim и удаляет использованный шифротекст после обработки. Plaintext не
записывается в state/event/intent/history/preview; repr контекста скрывает secrets.
Telegram-аудит маскирует runtime input; удаление входящего secret message выполняется
адаптером вне DB chat lock. Неизвестные и недоступные slash-команды не принимаются
как runtime secret input; только legacy-поле пароля OBIS допускает их как ввод.

## Исполнение и навигация

Пользовательский контекст предоставляет доверенный адаптер; event user/chat ID
должны ему соответствовать. Runtime пока обслуживает только приватные чаты.
Подделанная скрытая кнопка и URL-кнопка не продвигают сценарий. Bindings присваивания
сначала вычисляются целиком, поэтому порядок ключей не меняет результат.

Условия и явный разбор text/integer/choice не используют eval. Bool не равен
числу 0/1. Пропущенное nullable-поле читается как None; обязательное значение
отсутствовать не может. V2 добавляет типизированные list/object, ReferenceValue.path,
contact/media/secret events. Contact проверяет owner; накопление media дедуплицирует
message_id и проверяет объявленный лимит коллекции. Исполнение ограничено общим
бюджетом 32 автоматических шагов за событие, включая Call/Return/Replace.

Call сохраняет frame родителя и запускает pinned ребёнка с его initial_data и явными
inputs. Данные родителя не смешиваются с локальными данными ребёнка. Return проверяет
outcome/outputs, восстанавливает родителя и копирует только назначенные результаты.
Frames переживают рестарт. Replace закрывает прежнюю сессию и создаёт новую с новым
ID, сброшенной ревизией и без переноса неявных данных. Receipt связывает исходное
событие с результирующей сессией, поэтому replay не повторяет замену.

Динамические кнопки разворачиваются из typed object collection. Сохранённый экран
закрепляет action snapshot (template/target/assignments/item); поздний callback или
reply использует показанный выбор независимо от нового порядка источника. Runtime
повторно проверяет опубликованный переход и применимость условия. Rich screen
поддерживает до двадцати дополнительных текстовых сообщений и десяти фото/видео,
сохраняет все известные message IDs и не пересылает автоматически частичный unknown
результат. Эти возможности не означают завершение feature-specific edit/ephemeral миграций.

Resume возвращает текущий узел без повторного Action. Глобальная cancel/main_menu
закрывает сессию, освобождая чат; прежний node_id остаётся последним шагом в истории.
Локальная отмена или Back задаются обычными кнопками и переходами в схеме.
End с `feature` передаёт управление через presentation-адаптер после commit и claim.
Девять совместимых входов используют те же публичные entry points, что прежние
handlers. Номера 6–7 здесь относились к исходному UI_FLOW_EDITOR_PLAN.
Telegram уже использует `follow_returns`: v1 End с
`return_flow` создаёт новую сессию на текущей публикации целевого Menu/Input.
Данные исходной формы не переносятся. Source state, DB-делегат, target state,
дедупликация и intent фиксируются вместе. `UiFlowEvent.result_session_id` хранит
результирующую сессию, сохраняя исходную идентичность события и корректный повтор.
Подтверждение/отмена и корень объединяются в один проверенный экран с клавиатурой
целевой версии. Чистый DialogService не отправляет сообщений и не вызывает handlers.
Preview возвращает только намерение `screen.return_flow`. См. [SURVEY.md](SURVEY.md).

Явный вход в административное главное меню может атомарно отменить прежнюю сессию
и создать новую на текущей публикации. Неявная смена версии активной формы запрещена.
`navigation_entries.study` задаёт Menu-узел для глобального входа в «Учёбу».

Для мониторинга добавлены `ui_user_locations` и `ui_user_transitions`: runtime обновляет
их вместе с событием, legacy-наблюдатель — после успешного исходного REQUEST.
Данные формы не копируются. История имеет собственный keyset ID, без предположения
о бесконечном числовом росте Telegram update_id. Миграция переносит старую runtime-
историю. Семантика owner/перезапуска и read-only мониторинг описаны в
[MONITORING.md](MONITORING.md).

## Проверки

Используется development PostgreSQL из Docker Compose, без production-данных.
Обычные DB-тесты используют rollback/savepoints из tests/conftest.py. Проверки
конкуренции и новых DI-контейнеров используют отдельные временные схемы и реальные
commit. После проверки временные схемы удаляются.

Миграционные тесты применяют upgrade/downgrade/re-upgrade в изолированных схемах,
сохраняя прежние строки и v1-позиции. Downgrade этапа 6 блокирует writers и отказывает
до DDL при новых несовместимых состояниях/данных вместо их удаления. Общая схема
development не откатывается. `alembic check` проверяет ORM и применённую миграцию.
Restart/replay, concurrent claims, late results, expiry, partial delivery и rich
publication проверяются отдельно. Локальный HTTP-мок и browser preview не являются
доказательством live Telegram; feature cutover этапов 7–12 здесь не заявляется.
