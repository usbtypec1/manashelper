# Runtime сценариев: этапы 2–8

Реализованы исполнитель между пользовательскими событиями, PostgreSQL-хранилище,
Dishka-композиция, Telegram-адаптер, административный API и Vue-редактор.
Меню администратора используют runtime; прочие пользователи сохраняют старые маршруты
до этапа выпуска. Жизненный цикл доставки описан в [TELEGRAM.md](TELEGRAM.md),
общая проекция положения пользователей — в [MONITORING.md](MONITORING.md).

## Приложение

Чистый движок находится в `src/ui_flows/`, его хранилище задаётся контрактами
`ports/repositories.py`. Интеграции и DI находятся в `src/manashelper/modules/ui_flows/`.
Общая SQLAlchemy Base находится в `src/common/database.py`.

- `application/flows.py::FlowService`: создание и чтение черновика, сохранение с
  expected_revision, публикация и активация существующей версии.
- `application/dialogs.py::DialogService`: запуск, чтение состояния и обработка
  нормализованного события с проверкой пользователя, ревизии и update_id.
- `application/interpreter.py::FlowInterpreter`: исполнение пяти видов узлов до
  ожидания или завершения. SQL и Telegram внутри исполнителя отсутствуют.
- `application/delegates.py::DelegateRegistry`: явные async-делегаты с версией
  контракта и проверкой типов аргументов, выходов и исходов.
- `manashelper/modules/student_questions/survey_delegates.py`: адаптеры к StudentQuestionsService.
- `manashelper/modules/ui_flows/provider.py::UiFlowsProvider`: REQUEST-зависимости
  приложения. Для этой композиции нужны CoreProvider и StudentQuestionsProvider;
  перед созданием вызвать load_models. Сам движок импортируется без приложения и ORM.

Provider регистрируется в `main.py`; административный `/flow_demo` остаётся входом
для проверки отдельных сценариев. Реестр содержит два транзакционных делегата опроса.
На этапе 6 зарегистрированы девять handoff-возможностей и общий production-документ
главного меню. Передача управления использует публичные presentation entry points;
HTTP preview показывает намерение без вызова реального адаптера.

## Хранилище

Миграция `84ba87e64380` добавляет только четыре таблицы:

| Таблица | Содержимое |
| --- | --- |
| ui_flows | Текущий черновик, его ревизия и указатель опубликованной версии |
| ui_flow_versions | Снимок схемы, номер версии, исходная ревизия, автор и время |
| ui_dialog_sessions | Пользователь/чат, закреплённая версия, шаг, статус, данные и ревизия |
| ui_flow_events | Уникальный update_id, сессия, предыдущий/следующий шаг и исход |

В истории нет текста сообщений и копии полей формы. Данные ответа находятся только
в необходимом состоянии сессии и в таблице владельца бизнес-функции. repr состояния
и InputEvent скрывает ввод; обработчики не должны логировать полные модели и
Pydantic validation input. Закрытые payload и старые экраны очищаются ежедневным
заданием через семь дней; активные данные и receipts сохраняются. См. [RELEASE.md](RELEASE.md).

Одна БД предполагает одного Telegram-бота; update_id уникален в пределах этого
экземпляра. Поддержка нескольких токенов потребует отдельного пространства идентичности.

## Публикация и версии

Черновик можно сохранить с семантическими ошибками для последующего редактирования.
Публикация проверяет статический контракт, наличие делегатов, доступных features
и опубликованных сценариев возврата. Чистый контракт допускает самовозврат, но
Telegram-адаптер исполняет `return_flow` атомарно с завершением исходной сессии;
целевая публикация должна начинаться с Menu/Input, ограничивая автоматические циклы.
HTTP-публикация и активация проверяют Telegram HTML, размеры отрендеренных сообщений
и неоднозначность подписей reply-кнопок.

Сохранение увеличивает draft_revision. Публикация блокирует строку сценария,
назначает следующий номер версии и меняет указатель в одной транзакции. Повтор
публикации той же ревизии возвращает прежнюю версию и не отменяет сделанный после
неё rollback. Повтор со старой ревизией после нового редактирования даёт конфликт.
Активация версии проверяет expected_published_version и совместимость контрактов.

Начатая сессия всегда читает свою FlowVersion, даже после публикации новой схемы.
У репозитория нет операции изменения снимка версии. Версии делегатных контрактов
в Action также должны оставаться совместимыми: изменение контракта требует нового номера.

## Транзакции и конкуренция

Запуск и обработка события проходят внутри repository savepoint, использующего
тот же AsyncSession, что делегат и бизнес-сервис. Savepoint не делает commit:
окончательное решение остаётся у CoreProvider при завершении REQUEST.

1. Взять `pg_advisory_xact_lock(chat_id)`, затем загрузить сессию с FOR UPDATE.
   Для первого запуска блокировка работает до появления строки сессии.
2. Проверить владельца, уникальный update_id и expected_revision.
3. Выполнить переходы и транзакционные делегаты до ожидания.
4. Сохранить состояние и запись события; освободить savepoint.
5. Завершить REQUEST. Исключение или cancellation откатывает весь request.

Частичный unique index дополнительно запрещает две активные сессии на один чат.
Разные update_id с одной ревизией конкурируют: один проходит, второй получает
StaleEventError. Повтор того же update_id возвращает текущее состояние с исходом
duplicate, не повторяя действие; состояние может быть уже дальше первоначального
ответа. Для invalid_input событие учитывается, но шаг, данные и ревизия не меняются.

Если вызывающий код перехватил ошибку, savepoint всё равно отменяет запись делегата,
переход и дедупликацию этого события. Тот же update можно безопасно повторить после
устранения ошибки. Ожидаемый исход делегата, например already_submitted, проходит
обычным переходом. Внешние HTTP-операции и внешние записи не допускаются в текущих
делегатах: они требуют отдельной схемы подготовки/применения без долгой блокировки.

## Исполнение и навигация

Пользовательский контекст предоставляет доверенный адаптер; event user/chat ID
должны ему соответствовать. Runtime пока обслуживает только приватные чаты.
Подделанная скрытая кнопка и URL-кнопка не продвигают сценарий. Bindings присваивания
сначала вычисляются целиком, поэтому порядок ключей не меняет результат.

Условия и явный разбор text/integer/choice не используют eval. Bool не равен
числу 0/1. Пропущенное nullable-поле читается как None; обязательное значение
отсутствовать не может. Исполнение ограничено 32 автоматическими узлами за событие.

Resume возвращает текущий узел без повторного Action. Глобальная cancel/main_menu
закрывает сессию, освобождая чат; прежний node_id остаётся последним шагом в истории.
Локальная отмена или Back задаются обычными кнопками и переходами в схеме.
End с `feature` передаёт управление через presentation-адаптер после commit и claim.
Девять входов реализованы на этапе 6; они используют те же публичные entry points,
что прежние handlers. На этапе 7 Telegram включает `follow_returns`: End с
`return_flow` создаёт новую сессию на текущей публикации целевого Menu/Input.
Данные исходной формы не переносятся. Source state, DB-делегат, target state,
дедупликация и intent фиксируются вместе. `UiFlowEvent.result_session_id` хранит
результирующую сессию, сохраняя исходную идентичность события и корректный повтор.
Подтверждение/отмена и корень объединяются в один проверенный экран с клавиатурой
целевой версии. Чистый DialogService не отправляет сообщений и не вызывает handlers.
Preview возвращает только намерение `screen.return_flow`. См. [SURVEY.md](SURVEY.md).

Явный вход в административное главное меню может атомарно отменить прежнюю сессию
и создать новую на текущей публикации. Неявная смена версии активной формы запрещена.
`navigation_entries.study` задаёт Menu-узел для глобального входа в «Учёбу».

На этапе 6 добавлены `ui_user_locations` и `ui_user_transitions`: runtime обновляет
их вместе с событием, legacy-наблюдатель — после успешного исходного REQUEST.
Данные формы не копируются. История имеет собственный keyset ID, без предположения
о бесконечном числовом росте Telegram update_id. Миграция переносит старую runtime-
историю. Семантика owner/перезапуска и read-only мониторинг описаны в
[MONITORING.md](MONITORING.md).

## Проверки

Используется development PostgreSQL из Docker Compose, без production-данных.
Обычные DB-тесты используют rollback/savepoints из tests/conftest.py. Проверки
конкуренции и новых DI-контейнеров используют отдельные временные схемы и реальные
commit. После проверки временные схемы удаляются.

Отдельный тест применяет upgrade, downgrade и повторный upgrade миграции в
изолированной схеме, сохраняя существующую строку users. Общая схема development
не откатывается. `alembic check` проверяет соответствие ORM и применённой миграции.
