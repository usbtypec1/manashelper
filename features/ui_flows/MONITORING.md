# Меню и наблюдение за пользователями: этап 6

Реализованы импорт основного меню, переходы в прежние функции и мониторинг runtime/FSM.
Переключение меню пока доступно только приватному администратору. Другие пользователи
сохраняют прежние маршруты; их разрешённые приватные действия наблюдаются без копии
данных формы. Студенческий опрос также перенесён для администратора на этапе 7;
общий выпуск остаётся этапом 8. См. [SURVEY.md](SURVEY.md).

## Главное меню и «Учёба»

`modules/ui_flows/menus.py::main_menu_document` воспроизводит существующие подписи,
ряды reply-кнопок, пять локалей, обе темы и guards `eders_enabled`. При запуске бота
`main_menu` создаётся/публикуется только при отсутствии; сохранённые правки, версии
и указатель публикации не перезаписываются.

У администратора bare `/start` открывает опубликованный корень. Активная форма
отменяется и новый корень создаётся в одной транзакции с одним входящим событием.
Для «Учёбы» используется `navigation_entries.study`; проверка допускает только Menu.
Редактор обновляет этот alias при переименовании и позволяет выбрать его в «Полях данных».

Показанные runtime reply-кнопки обрабатываются до глобальных текстовых переходов,
поэтому изменение текста/цели кнопки в графе сохраняет смысл схемы. Глобальные Back
и Studies могут очистить незавершённый ввод и открыть текущую опубликованную версию.
Маршрут bare `/start` отклоняет payload: survey/ad deep links продолжают попадать
в существующие обработчики, со своим порядком и проверками.

## Передача управления

End со статусом `handed_off` и зарегистрированным `feature` закрывает runtime-сессию.
Состояние, событие, метаданные и intent фиксируются до сети. Claim сохраняет unknown
до вызова общей presentation-функции. Она получает исходное Message, FSMContext и
проверенный RuntimeUser; callback не использует автора bot-message как пользователя.
Не создаются поддельные Update и не вызываются aiogram handlers напрямую.

| Feature | Общий presentation entry point |
| --- | --- |
| `food_menu` | Food menu `show_food_menu` |
| `marketplace` | Advertisements `send_marketplace_menu` |
| `settings` | Telegram platform `show_settings` |
| `schedule` | Schedule `show_timetable_menu` |
| `attendance`, `grades` | OBIS `show_attendance`, `show_grades` |
| `study_week` | Study week `show_study_week` |
| `eders`, `eders_materials` | Eders `show_eders` с явным фильтром |

Прежние routers используют те же входы. Данные OBIS/Eders/Study week читаются из
снимков; меню не запускают внешнюю синхронизацию. Адаптер дополнительно запрещает
Eders/Study week при отключённой настройке, независимо от конфигурации кнопки.

После успешного entry point записывается legacy-положение, затем intent получает
sent. Для нескольких сообщений feature нет единственного message_id, поэтому он
может быть null. Неопределённая отправка не повторяется автоматически. Повтор того
же события не выполняет feature ещё раз. Явный возврат в корень создаёт новый запуск.
На этапе 7 реализован атомарный `return_flow` к опубликованному Menu/Input.
Preview показывает feature/return как намерение, без реального запуска или записи.

## Проекция и история

Миграция `8e3edc9cfd80` добавляет:

| Таблица | Содержимое |
| --- | --- |
| `ui_user_locations` | Пользователь/чат, owner, runtime session ID либо handler/FSM state, update ID и время |
| `ui_user_transitions` | Собственный keyset ID, update ID, owner, версия, шаги, исход и время |

Миграция переносит прежние runtime-наблюдения. Downgrade удаляет только новые таблицы,
сохраняя пользователя, версии, сессии, поля формы и прежние события. Общая development
схема применена вперёд; обратный переход проверяется в изолированной схеме.

Runtime-переход обновляет проекцию и историю в той же транзакции, что состояние,
дедупликация и DB-делегаты. Общая история имеет один итоговый переход на update.
При handoff сохраняются исходный шаг/версия, а конечный шаг и owner становятся legacy.

`UiFlowObservationMiddleware` работает после проверки приватности и только для
совпавшего успешно завершившегося handler. Оно ставит наблюдение в AfterRequestActions;
запись выполняется после commit исходного REQUEST и до освобождения очереди чата.
Читается только `FSMContext.get_state()`, не `get_data()`. Runtime-flagged handlers
наблюдаются самим координатором; активный runtime имеет приоритет над поздней legacy-записью.
Ошибка handler/commit не создаёт успешного наблюдения. Ошибка записи телеметрии
логируется после rollback своего scope и не отменяет уже завершённую бизнес-операцию.

Очередь чата, advisory lock и receipts обеспечивают порядок и защиту от повторов.
Числовой рост update_id не используется для выбора положения: после длительного
простоя Telegram может изменить последовательность. История использует собственный
возрастающий ID. См. [описание Update](https://core.telegram.org/bots/api#update).

При старте бота legacy owner становится unknown: MemoryStorage утрачен. Время,
handler и имя прежнего state остаются последним наблюдением, не восстановленной формой.
Runtime-сессии остаются на своей версии и восстанавливаются прежним механизмом.
Перезапуск административного API не сбрасывает положение пользователей.

## API и экран пользователей

GET `/users/locations` получает страницу зарегистрированных ID через публичный
UsersQuery и добавляет только метаданные UI flows. Не наблюдавшиеся пользователи имеют
`owner=unknown`, `updated_at=null`. GET `/users/{id}/location` используется для поиска.
История доступна через `/users/{id}/transitions`; cursors подписаны и привязаны к запросу.

Read-only граф запрашивается через GET `/flows/{id}/versions/{version}`. Он соответствует
версии сессии, даже если черновик или указатель публикации уже изменены. Редактирование
использует отдельный черновик; просмотр пользователей не меняет его или состояние бота.
Список и история имеют пагинацию; видимая страница обновляется каждые пять секунд.

`runtime` означает активный ожидающий шаг. `legacy` означает последний наблюдавшийся
handler/FSM state. `unknown` не подтверждает текущего положения. Отправка Telegram API
не означает прочтения сообщения; для legacy-действий без runtime intent статус доставки
не выводится как установленный. Ответы форм, пароли, FSM data и тексты подготовленных
экранов в мониторинг не возвращаются.
