Продолжение разработки: [весь UI через оркестратор](ui_flows/ORCHESTRATION.md).
Новый план включает aiohttp/webhook, fullscreen Mini App, DB-локализацию,
композицию небольших сценариев и окончательное удаление aiogram FSM.
Этапы ниже описывают уже созданный редактор и первоначальный пилот.

Статус: этапы 1–8 реализованы и проверены локально. Дата: 2026-11-01.
Добавлены типизированные контракты, статический валидатор, JSON Schema, OpenAPI
и контрольные документы меню/опроса. Подробности: [контракт версии 1](ui_flows/CONTRACT.md).
Добавлены исполнитель, PostgreSQL-хранилище, REQUEST provider и административный

Добавлен [административный API](ui_flows/ADMIN_API.md) с одноразовым входом и preview.
Добавлен [Vue-редактор](../src/admin-ui/README.md), сборка и исполнение инструментов через Bun.

## Цель и границы

Администратор собирает интерфейс Telegram-бота в браузере: меню, тексты, кнопки,
шаги форм и переходы. Python-делегаты вызывают существующие сервисы. Администратор
видит текущий экран или ожидаемый ввод пользователя и историю переходов.

Первая завершённая версия включает главное меню, меню «Учёба» и студенческий опрос.
Опрос проверяет ввод, ветвления, отмену, подтверждение замены и финальное сохранение.
Остальные формы продолжают работать через существующие обработчики; их шаги видны
через наблюдение за FSM, но восстановление после перезапуска гарантируется только
для перенесённых сценариев. Пароли OBIS, загрузка альбомов и рассылка не переносятся.

В первой версии нет параллельных веток, таймеров, произвольных скриптов, BPMN,
магазина плагинов, совместного редактирования и принудительного перемещения
пользователей администратором. Поддерживается один активный диалог на приватный чат.

## Основание в текущем коде

- `platform/telegram/navigation.py`: главное меню и «Учёба» заданы Python-кодом.
- `platform/telegram/routers/navigation.py`: навигация очищает текущий FSM.
- `platform/telegram/filters/translated_text.py`: reply-кнопки определяются текстом
  в текущей локали с поддержкой обеих тем.
- `modules/student_questions/router.py`: шаги, ветвления, ввод и session ID уже
  реализованы; `service.py` и `repository.py` сохраняют завершённый ответ.
- `platform/telegram/dispatcher.py`: порядок роутеров значим; диспетчер использует
  стандартное хранилище FSM в памяти. RateLimit и PerChatOrdering сохраняются.
- `core/provider.py`: транзакция фиксируется при нормальном завершении REQUEST.
- `platform/i18n/catalog.py`: gettext, английский fallback, локаль и тема пользователя.
- На момент планирования в `pyproject.toml` не было веб-сервера и frontend-зависимостей.
  На этапе 4 добавлены FastAPI и Uvicorn; frontend относится к этапу 5.

Перед переносом каждой следующей функции отдельно изучаются её роутер, сервис,
репозиторий и тесты. Этот план не предполагает, что текущие обработчики можно
автоматически превратить в граф.

## Архитектура

- Frontend: Vue 3, TypeScript, Vite, Vue Flow; отдельный каталог `src/admin-ui/`.
- Движок и управление схемами: `src/ui_flows/`, с domain/application и ports.
- Общая ORM Base: `src/common/database.py`.
- Адаптеры хранилища, Telegram и admin API, rollout и provider:
  `src/manashelper/modules/ui_flows/`; регистрация в существующем dispatcher.
- Административный HTTP-адаптер: FastAPI, отдельная точка запуска
  `manashelper.admin_main`; общая БД и те же application-сервисы.
- Общая HTTP-инфраструктура размещается в `platform/web/`, когда она действительно
  нужна для жизненного цикла, авторизации и обработки ошибок.
- Бот остаётся единственным потребителем Telegram updates через long polling.
  Веб-процесс не запускает polling, scheduler и отправку пользовательских сообщений.
- Оба процесса вызывают `bootstrap.load_models()` и создают собственные контейнеры.
  Используются общие CoreProvider и Base; бизнес-зависимости сохраняют REQUEST scope.

Vue Flow отвечает за граф, а Python — за проверку и исполнение. Координаты узлов,
масштаб и выделение не участвуют в выборе переходов. Первая версия читает указатель
опубликованной схемы из БД, без кеша, который пришлось бы инвалидировать между процессами.

## Контракт схемы

Версионируемый JSON-документ содержит `schema_version`, идентификатор сценария,
начальный узел, узлы со стабильными ID, кнопки со стабильными ID и переходы.
Метаданные расположения графа отделены от исполняемого содержимого.

| Узел | Настройки |
| --- | --- |
| Menu | Текст, reply/inline-клавиатура, строки кнопок, доступность кнопок |
| Input | Поле результата, тип text/integer/choice, обязательность, ограничения, ошибка |
| Condition | Поле, разрешённый оператор, значение, ветка по умолчанию |
| Action | Идентификатор делегата, входные параметры, поле результата, ожидаемые исходы |
| End | Результат формы и переход к разрешённому меню |

Кнопка задаёт переход, ввод фиксированного значения, запуск зарегистрированной
возможности, URL, возврат или отмену. URL-кнопка не продвигает состояние: открытие
ссылки не даёт боту подтверждения действия пользователя.

Условия поддерживают `eq`, `ne`, `in`, `exists`, сравнения чисел и простые группы
`all`/`any`. Доступны только объявленные поля контекста и разрешённые capabilities,
например `eders_enabled`. Нет `eval`, Python/JavaScript-кода и доступа к атрибутам объектов.

Делегат имеет типизированные входы, выходы и ожидаемые ошибки. Автор схемы выбирает
его из каталога; импорт Python-модуля из JSON запрещён. Делегаты обращаются к публичным
сервисам владельца функции, а не к роутерам, ORM или чужим репозиториям. Логику
сохранения опроса сохраняет `StudentQuestionsService`.

Валидация проверяет ссылки, типы, доступность делегатов, достижимость узлов,
обязательную ветку по умолчанию, шаблонные параметры, клавиатуры и выход из формы.
Циклы меню допустимы; циклы автоматических шагов без ожидания запрещены.
Дополнительная защита исполнения — не более 32 автоматических шагов на одно событие.
Скрытая кнопка также недоступна для исполнения при подделанном callback.

## Тексты, переводы и темы

Системные сообщения, команды и неизменённые функции продолжают использовать `.po`
и существующий gettext. Существующие тексты доступны редактору как ссылки на
разрешённые message keys; список ключей поддерживается извлекаемым кодом/ресурсом.

Редактируемые в браузере шаблоны хранятся вместе с версией сценария в БД с вариантами
`en`, `ru`, `ky`, `tr`, `zh` и поддержкой существующих тем. Это необходимое расширение
текущего правила о хранении всех интерфейсных текстов в `.po`: иначе изменение
текста в браузере потребует записи в checkout, компиляции каталогов и доставки сборки.
При реализации это различие нужно явно внести в проектную документацию и AGENTS.md.

Для нового шаблона английский вариант обязателен. Порядок выбора: вариант текущей
темы и локали, базовый вариант локали, вариант темы на английском, базовый английский.
Начальная импортированная версия должна воспроизводить обе текущие темы и все пять
локалей; переключение языка/темы перерисовывает текущий экран без потери данных формы.

Разрешены только именованные подстановки из объявленного контекста. Динамические
значения экранируются `escape_html` до подстановки. Поддерживаемые HTML-теги, параметры,
длина сообщений, caption и кнопок проверяются до публикации. Превью не выполняет HTML
шаблона как произвольную разметку страницы браузера.

## Хранение и версия процесса

Сущности ниже — логическое разделение; окончательные имена таблиц фиксируются в миграции.

| Сущность | Назначение |
| --- | --- |
| Flow | Стабильный ID и указатель текущей опубликованной версии |
| FlowDraft | Редактируемый документ и счётчик ревизии для защиты от потери изменений |
| FlowVersion | Неизменяемая схема, версия делегатных контрактов, автор и время публикации |
| DialogSession | Чат/пользователь, версия схемы, шаг, данные формы, статус, ревизия состояния |
| FlowEvent | ID входящего события, переход, время и исход без копии введённого текста |
| DeliveryIntent | Подготовленный экран, привязка к ревизии сессии и результат отправки |
| UserLocation | Проекция текущего положения, включая наблюдение за legacy FSM |

Новая сессия фиксирует FlowVersion. Публикация и откат меняют только указатель для
новых запусков. Активная форма продолжает прежнюю версию. Для применения новой версии
к открытому меню пользователь явно возвращается в корень; введённые данные формы
самопроизвольно не мигрируют. Удалять версии с активными сессиями нельзя.

При возврате из формы создаётся/открывается меню текущей опубликованной версии;
завершённая сессия формы остаётся в истории. События финального сохранения опроса и
закрытия сессии должны быть атомарны в одной БД-транзакции.

Данные полей хранятся только там, где нужны для продолжения формы. Пароли, токены и
OBIS credentials не входят в общий контекст. API мониторинга выдаёт только разрешённые
поля; ответы опроса не копируются в переходы, логи и сводку пользователей. До включения
production фиксируются срок хранения завершённых сессий и способ очистки их данных.

## Исполнение Telegram-событий

1. Нормализовать событие и определить владельца диалога: runtime или legacy.
2. В коротком REQUEST scope загрузить и заблокировать сессию, проверить revision
   и уникальность события. Для первого запуска использовать уникальный ключ чата
   и атомарное создание, поскольку отсутствующую строку нельзя заблокировать.
3. Проверить допустимость кнопки/ввода и выполнить автоматические узлы до ожидания.
   DB-делегаты используют ту же транзакцию. HTTP-чтения не удерживают блокировку
   сессии: подготовка и применение результата разделяются проверкой revision.
4. Сохранить данные, переход, проекцию положения и намерение показать экран.
   Завершить REQUEST scope нормальным образом, чтобы CoreProvider зафиксировал транзакцию.
5. Отправить или отредактировать экран после фиксации, затем в новом REQUEST scope
   записать Telegram message ID и исход доставки. Координатор организует эти scopes;
   бизнес-сервисы не вызывают произвольный commit поверх CoreProvider.

При ожидании пользователя нет открытой транзакции или coroutine, ожидающей ответа.
In-process PerChatOrdering сохраняется, но корректность также обеспечивается
БД-ограничениями и revision. Повторное событие не повторяет сохранение формы.

В callback помещаются короткий идентификатор сессии/токен, revision экрана и ID
кнопки через typed CallbackData. Payload проверяется на лимит 64 байта. Бот проверяет
владельца, чат, актуальность экрана и разрешённость перехода. Старые кнопки получают
понятный ответ; callback обязательно подтверждается.

Для reply-кнопок сохраняется отображение фактически показанных подписей в ID.
Неоднозначные подписи в одном экране запрещены. Нельзя достоверно отличить старую
reply-клавиатуру от нового сообщения с таким же текстом: разрешено только действие
текущего экрана. Для действий с необратимым результатом требуется inline-подтверждение.

Нет обещания exactly-once доставки Telegram-сообщения: сбой после отправки и до
записи результата неоднозначен. Неопределённая доставка отмечается отдельно, без
автоматического повтора бизнес-действия. Пользователь может восстановить текущий
экран; это перерисовка, а не повторное исполнение Action. Для первой версии
внешние изменяющие операции без согласованного ключа идемпотентности не регистрируются.

Проекция различает ожидаемый шаг, подтверждённую API отправку и неизвестную доставку.
Отправка не означает прочтения. Legacy-положение называется «последний наблюдавшийся
шаг»; после перезапуска потерянный MemoryStorage не показывается как восстановленная форма.

## Совместимость со старыми роутерами

- Runtime обрабатывает свой callback namespace и сообщения принадлежащей ему сессии,
  а не все сообщения. Владелец диалога определяется до legacy FSM handlers.
- Глобальная навигация, `/start`, язык/тема и deep links имеют явный приоритет.
  Сохраняется порядок survey deep link, advertisement deep link и обычного start.
- При входе в legacy-функцию runtime перестаёт владеть вводом и передаёт управление
  через явный адаптер публичной возможности. Нельзя синтезировать Update, подделывать
  текст кнопки или напрямую вызывать функцию aiogram handler.
- Если публичного входа нет, в рамках переноса извлекается минимальный общий
  application/presentation entry point; существующий роутер использует тот же вход.
- Глобальный выход отменяет runtime-форму и очищает legacy FSM, сохраняя текущую
  семантику Back. Кнопка «назад на шаг» внутри формы задаётся отдельно от отмены.
- Наблюдатель после успешного legacy handler записывает только имя функции/экрана,
  FSM state и время. Не сохраняет FSM data и текст ввода. Ошибка не считается
  успешным переходом; утраченные после рестарта состояния отмечаются неизвестными.

## Административный API и доступ

API работает отдельно от бота, под тем же origin, что frontend. Оператор один:
пользователь существующего `Settings.admin_chat_id` в приватном чате.
Планируемый вход — команда `/editor`, выдающая одноразовый короткоживущий билет.
Билет передаётся через fragment URL и обменивается POST-запросом на серверную
сессию; хранится только hash билета, использование атомарно. Постоянный секрет
не размещается в frontend, URL query, LocalStorage и логах.

Сессия использует HttpOnly/Secure cookie, SameSite и защиту mutating-запросов
от CSRF с проверкой origin. Нужны истечение, выход и отзыв сессии. Новые настройки
base URL/секретов добавляются в Settings и пример окружения без реальных значений.
Команда и ошибки получают ключи во всех пяти каталогах; `/editor` регистрируется
только для admin chat по аналогии с существующей административной командой.

Минимальный контракт `/admin/api/v1`:

| Операция | Назначение |
| --- | --- |
| POST /auth/exchange; POST /auth/logout | Вход и завершение сессии |
| GET /flows; POST /flows; GET /flows/{id} | Каталог и создание сценария |
| GET, PUT /flows/{id}/draft | Чтение и сохранение с expected_revision |
| POST /flows/{id}/validate | Ошибки с node_id, button_id и путём поля |
| POST /flows/{id}/preview | Безопасный шаг симуляции с тестовым контекстом |
| POST /flows/{id}/publish | Атомарная публикация проверенной ревизии |
| GET /flows/{id}/versions; POST /flows/{id}/activate | История и откат указателя |
| GET /delegates | Публичные схемы входов/выходов, допустимые исходы и ограничения |
| GET /users/locations; GET /users/{id}/transitions | Положение и история пользователя |

Ошибки: 401 без сессии, 403 без доступа, 404 для неизвестного ресурса,
409 для конфликта ревизий, 422 для неверной схемы. Списки используют ограниченную
cursor-пагинацию. Повтор публикации одной ревизии не создаёт дубли версий.
В первой версии мониторинг обновляется опросом API; WebSocket не нужен.

До реализации frontend фиксируется локальный OpenAPI-контракт с примерами ошибок,
моделями авторизации, пагинацией и правилами повторов. Он является источником
TypeScript-типов; сервер проверяется на соответствие. Postman workspace не создаётся
и ничего не публикуется ради одного плана.

## Проверка и критерий завершения

- Unit: допустимые переходы, типы данных, условия, возврат/отмена, автоматические циклы.
- PostgreSQL: версии, ограничения, первый конкурентный запуск, дедупликация,
  конкурентные updates, rollback/cancellation и атомарность финального сохранения.
- Telegram: пять локалей и обе темы, HTML, reply/inline, старые кнопки, feature flags,
  приоритет роутеров, legacy-переходы и ошибка/неопределённый результат доставки.
- API: авторизация, CSRF, билеты входа, expected_revision, пагинация, отсутствие
  секретов/ответов в мониторинге и побочных эффектов в preview.
- Frontend: связать кнопку с экраном, изменить раскладку, исправить ошибку схемы,
  сохранить, опубликовать, выполнить rollback и увидеть пользователя на графе.
- Перезапуск: восстановить форму на прежнем шаге без повторного DB-действия.
- Регрессии: текущая навигация, опрос, транзакции CoreProvider и затронутые функции.
- Репозиторий: Ruff, format, strict mypy, соответствующие pytest на development
  PostgreSQL и скомпилированных каталогах; сборка/typecheck frontend и проверка OpenAPI.

Для воспроизводимого E2E использовать development DB и изолированный Telegram-адаптер;
проверку реальным ботом выполнять на тестовом токене. Production не используется для тестов.

Работа над первой версией завершена, когда меню и опрос управляются через редактор,
публикация не требует рестарта, состояние восстанавливается, оператор видит положение
пользователя, а существующие функции и правила опроса сохраняются. После этого
остальные формы переносятся отдельными задачами с их собственными критериями приёмки.
